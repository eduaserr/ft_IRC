# IRC Commands

This document is the command map for `ft_irc`. The official 42 subject is
always the authority. RFC 1459, RFC 2812, and real-client behaviour are
supporting references.

## 1. Quick List

| Command | Purpose | Main phase | Main implementation area |
|---|---|---|---|
| `CAP` | Capability negotiation used by modern clients | Compatibility | `src/commands/CapCommand.cpp` |
| `PASS` | Supplies the server password | Registration | `src/commands/PassCommand.cpp` |
| `NICK` | Sets or changes the nickname | Registration | `src/commands/NickCommand.cpp` |
| `USER` | Supplies username and real name | Registration | `src/commands/UserCommand.cpp` |
| `PING` | Tests that the connection is alive | Transport/protocol | `src/commands/PingCommand.cpp` |
| `PONG` | Replies to `PING` | Transport/protocol | Usually generated by `PingCommand` |
| `JOIN` | Joins one or more channels | Channels | `src/commands/JoinCommand.cpp` |
| `PART` | Leaves one or more channels | Channels | `src/commands/PartCommand.cpp` |
| `PRIVMSG` | Sends a private or channel message | Messaging | `src/commands/PrivmsgCommand.cpp` |
| `QUIT` | Disconnects a client | Connection lifecycle | `src/commands/QuitCommand.cpp` |
| `TOPIC` | Reads or changes a channel topic | Channel modes | `src/commands/TopicCommand.cpp` |
| `INVITE` | Invites a user to a channel | Channel modes | `src/commands/InviteCommand.cpp` |
| `KICK` | Removes a user from a channel | Channel operators | `src/commands/KickCommand.cpp` |
| `MODE` | Reads or changes channel modes | Channel operators | `src/commands/ModeCommand.cpp` |

`PONG` is normally a reply rather than a command class. Numeric replies
such as `001`, `401`, `433`, and `461` are also server replies, not commands
received from the client.

## 2. Shared Flow

Every command follows this path:

```text
Client sends IRC line
    -> Server::recv()
    -> Client's Parser
    -> Message
    -> CommandRegistry lookup
    -> ICommand::execute(...)
    -> validate command-specific rules
    -> modify Client/Channel/Server state
    -> Replies formats response
    -> Client output buffer
    -> Server::send() on POLLOUT
```

`Parser` only understands IRC line syntax. It does not know whether `JOIN`
requires a key or whether `KICK` needs operator privileges.

`Message` only stores:

```text
prefix
command
params
trailing
hasTrailing
```

A concrete command owns semantic validation and state changes.

## 3. Command Contracts

### `CAP`

Purpose: handle capability negotiation sent by clients such as HexChat.

Typical input:

```text
CAP LS 302
CAP END
```

Parser result:

```text
command = CAP
params = ["LS", "302"]
```

Work:

- accept the capability request needed by the selected client;
- reply with `CAP ... LS` or `CAP ... ACK` when appropriate;
- allow the client to finish with `CAP END`;
- do not mark the client registered only because `CAP` completed.

Replies and registration state belong to the command/server layer, not to
`Parser`.

### `PASS`

Typical input:

```text
PASS secret
```

Preconditions:

- exactly one password parameter;
- client must not already be registered with a different state;
- password must equal the configured server password.

State change:

```cpp
client.setPasswordAccepted(true);
```

Relevant errors:

```text
461 ERR_NEEDMOREPARAMS
462 ERR_ALREADYREGISTERED
464 ERR_PASSWDMISMATCH
```

A successful `PASS` does not complete registration by itself.

### `NICK`

Typical input:

```text
NICK edu
```

Preconditions:

- exactly one nickname parameter;
- nickname syntax is valid;
- nickname is not already used by another client.

State change:

```cpp
client.setNickname("edu");
```

Relevant errors:

```text
431 ERR_NONICKNAMEGIVEN
432 ERR_ERRONEUSNICKNAME
433 ERR_NICKNAMEINUSE
```

If the client is already registered and changes nickname, the server must
also notify the relevant users according to the project contract.

### `USER`

Typical input:

```text
USER edu 0 * :Edu Serrano
```

Parser result:

```text
command = USER
params = ["edu", "0", "*"]
trailing = "Edu Serrano"
```

Preconditions:

- required parameters exist;
- username is valid according to the project policy;
- real name is present as the trailing parameter.

State change:

```cpp
client.setUsername("edu");
client.setRealname("Edu Serrano");
```

Relevant errors:

```text
461 ERR_NEEDMOREPARAMS
462 ERR_ALREADYREGISTERED
```

After `PASS`, `NICK`, and `USER` are all valid, the server sends the
registration numerics, beginning with `001 RPL_WELCOME`.

### `PING`

Typical input:

```text
PING :hello
```

Parser result:

```text
command = PING
trailing = hello
```

The command calls:

```cpp
Replies::pong(serverName, message.getTrailing());
```

Typical output:

```text
:ircserv PONG ircserv :hello
```

This is the first recommended end-to-end command because it does not require
channels or registration state.

### `JOIN`

Typical input:

```text
JOIN #general
JOIN #general secret
```

Preconditions:

- client is registered;
- channel name is valid;
- channel does not reject the client through invite-only, key, or limit mode.

State changes:

- create the channel if it does not exist;
- add the client to channel members;
- make the first member an operator;
- send the JOIN confirmation;
- send topic and names replies as required.

Relevant errors:

```text
401 ERR_NOSUCHNICK
403 ERR_NOSUCHCHANNEL
471 ERR_CHANNELISFULL
473 ERR_INVITEONLYCHAN
475 ERR_BADCHANNELKEY
```

### `PART`

Typical input:

```text
PART #general :leaving
```

Preconditions:

- channel exists;
- client is a member;
- optional reason is a trailing parameter.

State changes:

- broadcast the PART message to channel members;
- remove the client from the channel;
- delete an empty channel if that is the project policy.

Relevant errors:

```text
403 ERR_NOSUCHCHANNEL
442 ERR_NOTONCHANNEL
461 ERR_NEEDMOREPARAMS
```

### `PRIVMSG`

Typical input:

```text
PRIVMSG #general :Hola a todos
PRIVMSG edu :Hola
```

Preconditions:

- target exists;
- trailing message is present and non-empty according to project policy;
- client is allowed to speak to the target.

State changes:

- usually no persistent state change;
- enqueue the message for the target client or channel members;
- do not send the message back to the sender unless the protocol policy says so.

Relevant errors:

```text
401 ERR_NOSUCHNICK
403 ERR_NOSUCHCHANNEL
404 ERR_CANNOTSENDTOCHAN
412 ERR_NOTEXTTOSEND
461 ERR_NEEDMOREPARAMS
```

### `QUIT`

Typical input:

```text
QUIT :goodbye
```

State changes:

- broadcast the QUIT message where required;
- remove the client from every channel;
- remove the client from `_clients`;
- remove its descriptor from `_pollfds`;
- close the socket.

The cleanup must remain in the server ownership layer. A command may ask
for disconnection, but it should not directly manipulate `pollfd` storage.

### `TOPIC`

Typical inputs:

```text
TOPIC #general
TOPIC #general :New topic
```

Behaviour:

- without a trailing parameter, return the current topic;
- with a trailing parameter, set the topic;
- if `+t` is active, only channel operators may change it.

Relevant errors:

```text
403 ERR_NOSUCHCHANNEL
442 ERR_NOTONCHANNEL
461 ERR_NEEDMOREPARAMS
482 ERR_CHANOPRIVSNEEDED
```

### `INVITE`

Typical input:

```text
INVITE edu #general
```

Preconditions:

- target user exists;
- channel exists;
- inviter is a member and has the required operator privilege;
- target is not already a member.

State change:

- add the target to the channel invitation set;
- send an INVITE message to the target.

Relevant errors:

```text
401 ERR_NOSUCHNICK
403 ERR_NOSUCHCHANNEL
442 ERR_NOTONCHANNEL
443 ERR_USERONCHANNEL
482 ERR_CHANOPRIVSNEEDED
```

### `KICK`

Typical input:

```text
KICK #general edu :reason
```

Preconditions:

- channel exists;
- kicker is a member and channel operator;
- target is a member;
- required channel and target parameters exist.

State changes:

- broadcast the KICK message;
- remove the target from channel membership;
- clean any related invitation or operator state.

Relevant errors:

```text
401 ERR_NOSUCHNICK
403 ERR_NOSUCHCHANNEL
441 ERR_USERNOTINCHANNEL
442 ERR_NOTONCHANNEL
461 ERR_NEEDMOREPARAMS
482 ERR_CHANOPRIVSNEEDED
```

### `MODE`

Typical inputs:

```text
MODE #general
MODE #general +i
MODE #general +k secret
MODE #general +o edu
MODE #general +l 20
```

The command has two jobs:

1. query the current channel modes;
2. add or remove modes and consume mode parameters.

Mandatory channel modes for the project:

```text
i  invite-only
 t  topic restricted to operators
k  channel key
 o  channel operator
l  user limit
```

Preconditions:

- channel exists;
- client is a member when required;
- client has operator privileges for changes;
- each mode has the correct parameter and value.

Relevant errors:

```text
403 ERR_NOSUCHCHANNEL
472 ERR_UNKNOWNMODE
482 ERR_CHANOPRIVSNEEDED
461 ERR_NEEDMOREPARAMS
```

`MODE` should not be implemented as one giant block in `Server`. Put mode
parsing and channel state changes behind `Channel` methods, while the
command class validates the request and formats replies.

## 4. Where Each Piece Lives

### Shared protocol types

```text
include/Message.hpp   parsed data value
src/Message.cpp       constructors and getters
include/Parser.hpp    parser API and Parse_e states
src/Parser.cpp        CRLF buffering and IRC grammar
include/Replies.hpp   reply formatting API
src/Replies.cpp       PONG and numeric formatting
```

### Command classes

Create one class per command when the command layer starts:

```text
include/commands/PingCommand.hpp
src/commands/PingCommand.cpp
```

Each command should implement the shared `ICommand` contract. The exact
`execute()` signature must be agreed with the team before creating all
command files.

### Server and client integration

```text
include/Server.hpp   ownership, poll loop, transport API
src/Server.cpp       accept, recv, dispatch, send, cleanup
include/Client.hpp   connection identity, buffers, parser lifetime
src/Client.cpp       Client state implementation
```

`Server` owns clients and channels. Commands request state changes through
public APIs; they should not call `recv()`, `send()`, `close()`, or edit
`pollfd` directly.

## 5. Recommended Build Order

1. `PING` -> `PONG` end-to-end with `nc`.
2. `CAP`, `PASS`, `NICK`, and `USER` registration.
3. Emit `001` exactly once after registration completes.
4. `JOIN` and `PART` with member tracking.
5. `PRIVMSG` to users and channels.
6. `QUIT` and complete cleanup.
7. `TOPIC` and `INVITE`.
8. `KICK`.
9. `MODE` with `i`, `t`, `k`, `o`, and `l`.
10. Partial sends, malformed lines, flood limits, and real-client testing.

Do not implement command-specific parameter validation inside `Parser`.
For example, the parser may produce:

```text
KICK edu
command = KICK
params = ["edu"]
```

The `KICK` command then decides that the channel parameter is missing and
returns `461 ERR_NEEDMOREPARAMS`.

## 6. Where to Study

- `en.subject.pdf` in the repository: mandatory project requirements and
  allowed architecture.
- [RFC 2812](https://www.rfc-editor.org/rfc/rfc2812): formal client/server
  commands and numeric replies.
- [RFC 1459](https://www.rfc-editor.org/rfc/rfc1459): original IRC command
  and message grammar.
- [Modern IRC Docs](https://modern.ircdocs.horse/): readable explanations
  and examples of current client behaviour.
- [HexChat documentation](https://hexchat.github.io/): practical client
  behaviour and connection settings.
- `docs/ARCHITECTURE.md`: ownership and transport boundaries in this repo.
- `docs/PARSER.md`, `docs/MESSAGE.md`, and `docs/REPLIES.md`: focused guides
  for the protocol classes.

For every command, study in this order:

```text
subject requirement
  -> RFC command grammar
  -> required preconditions
  -> state changes
  -> positive reply
  -> relevant numeric errors
  -> nc test
  -> HexChat test
```
